摘要

SupplyGuard 是面向应急保供指挥的五级保障判定与复核闭环系统：对储备点向服务点的物资投送逐项判定 T1~T5（需求保障/运输可达/响应时效/签收闭环/证据一致性）并落库可追溯，配套缺口识别、调拨方案可行性判定与签收复核闭环。关键设计是"冻结快照＋规则判定＋统一证据层"：判定只读冻结基线，辅助证据异常一律降级、不阻断判定。215 项自动化用例全部通过，全新克隆环境实测 4 分 48 秒完整复现。

1. 问题与产品定位

1.1 场景与痛点

项内容
使用场景极端天气应急值守期间（含演练），保供值班员在指挥中心通过工作台查看 R1/R2 储备点向 P1/P2/P3 三个关键服务点投送饮用水/照明/急救包（W/L/R）的保障全局，并处理签收复核
现有做法值班员每 2 小时人工巡检一次仓库库存数字，投送与签收靠电话通知和纸质单据事后核对
现有做法的代价① 看不到"每个服务点的需求到底有没有被保障"的整体判定，只知道仓库还有多少货；② 签收单缺失时无法区分"没送到"与"送到了但没取证"，两类处置完全不同；③ 调拨方案是否可行靠经验估算，超时/运力不足到现场才发现；④ 全部过程无结构化留痕，事后无法追溯"当时为什么这么判"
你的做法以 run 为单元冻结现场快照，T1~T5 逐项规则判定并落库可追溯；缺口定位到（服务点, 物资）组合；三套调拨方案规则判定可行性；签收复核闭环自动生成新 run 复测

1.2 产品边界

做什么不做什么为什么不做
T1~T5 五级保障判定，逐任务独立落库可追溯不做真实设备的自动控制与自动调度执行数据来自模拟器与冻结场景文件，没有真实设备可控制；自动执行的误操作代价高于人工确认
缺口识别与三套调拨方案可行性判定不做任意多套方案的自动寻优固定三套方案的规则判定语义明确、可审计；寻优引入的启发式会削弱判定可解释性
签收复核闭环（待复核单→签收→幂等回执→自动复测）不做多用户权限体系演练场景为单人值守工作台，权限体系超出范围
取证失败可信降级（unknown/待验证，禁止"未送达"结论）不做基于取证失败的反向推断（如推断物资已丢失）证据 unavailable 只说明"取证失败"，不说明"未送达"；反向推断误报代价高于漏报
reality / what-if 双轨推演，父基线零污染不做对历史 run 的修改回写历史判定是追溯依据，可修改的历史会让全部结论失去可信度

1.3 与本项目的差异化

现有做法同类方案的常见问题本项目的处理
人工巡检 + 纸质记录只有库存数字，没有"保障成立与否"的逐任务判定T1~T5 五级判定逐任务独立落库，每个结论可追溯依赖与证据

  5. 辅助证据旁路：天气/RAG/ML/LLM/统计模块只写 evidence_v2，不参与判定结论（llm_explainer.py:6-9）。

2.2 技术选型与理由

选择备选方案为什么选它代价是什么
FastAPI + uvicornFlask / Django原生异步与 WebSocket 支持，Pydantic 请求体校验，接口即文档；与 MQTT 客户端共进程无框架冲突无模板引擎与 ORM，页面全静态；Pydantic 模型需手工同步
SQLite 单文件PostgreSQL / MySQL单机零部署，克隆即跑，评委环境无需装数据库；事务与触发器（快照不可变）够用无多用户并发与多机部署能力；JSON 函数依赖规避（无 JSON1 扩展环境已兼容）
MQTT（paho-mqtt）HTTP 轮询 / 纯 WebSocket 直推贴近真实物联网链路，模拟器与后端解耦，多订阅者天然支持需额外维护 broker；broker 缺失时实时链路降级、后台重试（实测可用）
冻结场景 JSON + run 快照直接读实时观测表判定输入确定化：同一场景任何时刻重放结果一致；what-if 推演在副本上叠加假设场景与实时观测需要显式种子机制保持同步
前端纯静态 HTML + 本地 Three.jsVue/React 构建链零构建依赖、离线可用，评委浏览器直接打开即完整可用无组件化，单文件 console.html 体积大、页面间耦合
规则判定（非模型判定）机器学习判定T1~T5 是明确的规则语义，确定性可审计、可回归比对；ML 只作辅助证据规则覆盖面有限，无法发现规则未定义的新模式

3.2 案例一：分页接口黑盒全绿，人工评审挖出三处线上隐患（2026-11-11）

① 我的要求（原始提问）

执行独立边界候选任务【runs列表分页查询接口】，只完成本任务，禁止提前实现其他调度功能。
任务目标：实现分页查询接口 GET /api/runs/paginated，支持 page、page_size，返回 {total, page, page_size, list}。业务要求：入参必填并做合法性校验；offset=(page-1)*page_size；超页返回空 list 不抛异常；老接口 GET /api/runs 等全部保留不动。
硬性保护约束：仅允许改动 run_store.py 增加分页查询函数、main.py 新增接口，其他文件一律不动。
自测验证清单：正常分页核对条数、非法参数报错、超页不报错、老接口行为不变、回归全部老接口。

（完整原文与截图见图 3-1。）

② AI 第一次给的方案

AI 动手前先指出矛盾：任务要求 is_deleted=0 过滤，但软删除已被我回滚，提问确认后按"不带 is_deleted 过滤"实现——这个提问环节是对的。交付 list_runs_paginated()：COUNT + LIMIT/OFFSET 取页，排序 ORDER BY created_at、无第二排序键；自跑 8 项 curl 用例全部通过。提交 89903d4。

③ 我发现的问题

黑盒全绿后，我做人工代码评审，发现三处单线程 curl 测不出来的隐患：

#输入错误表现为什么不能接受
1并发下分页查询的同时有新 run 写入total 的 COUNT 与 list 查询是两条独立 SQL，两次查询之间数据变化，total 与 list 错位分页总数和条目对不上
2page_size=10000参数只校验 ≥1、无上限，一次性读取大量行，慢查询恶意大 page_size 可打满数据库
3多条记录 created_at 完全相同排序只有 created_at、无唯一键兜底，翻页出现条目重复或丢失数据库排序不稳定，跨页结果不可信

判据：三处都不是业务功能错误，AI 自测清单里没有这些用例——黑盒测试与人工评审覆盖的不是同一层问题。

④ 我的纠偏

下发第二个独立任务【分页接口加固】：

任务目标：1. page_size 增加上限：最大允许 50，超值自动钳位到 50，不报错；2. 查询结果必须按 created_at DESC 倒序返回。
核心业务红线（重点）：易错坑 1：忘记限制 page_size，超大 page_size 直接全量拉取；易错坑 2：排序方向写反，变成 created_at 正序；原有返回结构（total、page、page_size、list）不能改动；只修改 run_store.py 的分页查询逻辑。

差异：第一版只要求"合法校验 + 分页公式"，加固版把"防护上限"与"排序稳定性"写成必做项，并把我预判的两个易错坑直接列成红线。

⑤ 验证结果

修复后实测（55 条数据）：page_size=10000 → 实际 page_size=50、total=55；page=1&size=3 → 最新 3 条在前；两页拼接等于完整倒序；老接口回归全 200。提交 0b0cd45（11-12）。对比见图 3-2，两次提交见图 3-3。
